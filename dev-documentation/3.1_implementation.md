# Phase 3: Advanced RAG, LLM Analysis & Backend API

## Overview

Phase 3 transforms FinSight from a simple financial data viewer into a **proper API product** — the kind that developers and algorithmic traders can call from their own systems. The key deliverables are:

1. **Public REST API** — the existing FastAPI endpoints, cleaned up and fully documented
2. **API Documentation Page** — an interactive, beautiful `/api-docs` page on the Next.js frontend
3. **Automated Test Suite** — `pytest`-based tests that validate the entire backend pipeline end-to-end
4. **Updated Project Docs** — MkDocs `docs/` pages reflecting the Phase 3 state of the system

> [!IMPORTANT]
> Phase 3 does **not** require building pgvector or Elasticsearch (those are stretch goals for Phase 5). The MVP milestone is: _"A robust FastAPI backend capable of querying precise financial metrics, with tests proving it works, and documentation explaining how to use it."_

#### [NEW] `src/backend/routers/search.py`

A minimal `POST /search` endpoint that accepts a payload with `ticker`, `statement_type`, and `fiscal_year` and returns the matching data from the DB. **This is the "API that users call with a payload"** described in the user request. This acts as a single unified query endpoint.

```
POST /search
{
  "ticker": "MAYBANK",
  "statement_type": "income_statement",   // or "balance_sheet" | "cash_flow" | "kpi" | "qualitative"
  "fiscal_year": 2024                      // optional; omit = latest
}
```

Response: the relevant financial record(s) in a consistent JSON envelope.

## User Review Required

> [!IMPORTANT]  
> **`POST /search` endpoint scope** — The "payload-based query" endpoint is the most design-sensitive part. I'm proposing a single `POST /search` that accepts `{ ticker, statement_type, fiscal_year }` and dispatches to the right table. An alternative is to keep using the existing `GET` endpoints. Do you prefer the unified search endpoint approach, or do the existing `GET` endpoints satisfy the "users send a payload" requirement?

> [!WARNING]
> **Test database** — Tests will use an **in-memory SQLite** database with fresh seed data. This means tests run offline (no Supabase needed), but SQLite and PostgreSQL behave slightly differently. All existing queries use standard SQLAlchemy so this should not be an issue, but be aware.

> [!NOTE]
> **`/api-docs` is a Next.js page, not the FastAPI Swagger UI** — The `/api-docs` frontend page is a human-readable guide for external developers. This is separate from the auto-generated FastAPI swagger at `/docs` on the backend. Both will exist; the frontend page is the "product-facing" docs.
